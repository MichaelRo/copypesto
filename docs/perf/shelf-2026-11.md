# Shelf: arrow keys, held arrows and collection switches (2026-11-12)

A Mac with a Paste import (1,079 clips back to 2018, most old ones in collections, mixed kinds) felt slow to scroll with
the arrow keys and the trackpad and to switch collections with ⌘[ / ⌘]. The existing benches
(`make bench-scroll`) never drove arrow keys or collection switches, and ran with Link Previews off on text-heavy
histories. `make bench-shelf` does both, on a history shaped like an import.

## How
`scripts/bench-shelf.sh [label]` builds the Profile app and launches it in UI-test mode with a seed (`imported`, `mixed`,
`large`), Link Previews on and answered by a local stub (`PESTO_UITEST_LINK_STUB_MS`, 250 ms; no request leaves the Mac).
The app drives itself (`benchArrowSteps`: 20 single presses 150 ms apart; `benchArrowHold`: 60 repeats 33 ms apart;
`benchCycleCollections`: ⌘] through every collection twice) through the code a key press runs, and signposts each step
from the key to the commit that shows it (`focusMove`, `collectionSwitch` with `collectionFilter` and `collectionApply`
inside). `RenderProbe` counts view bodies run between steps. `scripts/profile-scroll/shelf_report.py` prints p50 / p95 / max
and body runs per step. The Mac must be unlocked and awake. Single runs vary: run it twice before believing a small gap.

The `imported` seed (`ImportedSeed`) goes through `PasteMigrator` like a real import: 1,100 clips over 8 years, 15
collections holding most of the older ones, 2 smart collections (one over pictures), 60 pictures (more than the 40-entry
thumbnail cache), links whose previews were never fetched, GIFs, files that are gone, and sources that are not installed.

## Baseline (before any fix; M-series developer Mac, Profile build, `imported`)
| Drive | Commit time p50 / p95 / max | View bodies per step |
|---|---|---|
| One arrow press (20) | 39.9 / 58.3 / 59.7 ms | ClipboardCard 30 (max 49), GridView 2, OverlayRootView 1 |
| Held arrow (60 repeats) | 135 / 485 / 765 ms | ClipboardCard 69 (max 126), GridView 1.9, OverlayRootView 1 |
| ⌘] through the collections (36) | 70.7 / 84.3 / 132 ms (`collectionFilter` p95 15 ms) | ClipboardCard 16, GridView 2, OverlayRootView 1 |

This Mac feels fine to the person using it, and still misses a 16.7 ms frame on every press and takes 70 ms to switch
a collection. A Mac that is 2 to 4 times slower turns that into the lag described. What the numbers say:
- One press re-runs about 30 card bodies and the whole overlay root, so focus moving is not a one-card change.
- A held arrow piles work up: p95 485 ms per step means key repeats arrive faster than the shelf commits them.
- A switch rebuilds cards (16 bodies) after the old row was thrown away.

## After PR 2 (focus, collection switch, thumbnails off the main thread; same Mac, `imported`)
| Drive | Commit time p50 / p95 / max | View bodies per step |
|---|---|---|
| One arrow press | 12.4 / 15.4 / 20.2 ms (was 39.9 / 58.3 / 59.7) | ClipboardCard 3 (was 30), GridView 1 (was 2), OverlayRootView 0 (was 1) |
| Held arrow | 12.5 / 13.8 / 52.5 ms (was 135 / 485 / 765) | ClipboardCard 3.2 (was 69) |
| ⌘] through the collections | 68.6 / 73.7 / 78.9 ms (was 70.7 / 84.3 / 132) | ClipboardCard 8 (was 16), GridView 4 |

What changed, and what each part was worth (measured one change at a time):
- **Cards are `Equatable`** (`ClipboardCard+Equatable.swift`, `.equatable()` at the call site): a focus move no longer re-runs
  every realized card, only the two whose input changed. Held-arrow p95 485 → 33 ms, card bodies 69 → 15.
- **The glow colour lives in `ShelfGlow`**, read only by `ShelfBackground`: an arrow press no longer re-runs `OverlayRootView`
  (and the 0.6 s mesh-gradient animation no longer restarts it). Arrow step 27 → 12 ms.
- **One `ThumbnailService` per store, made off the main thread** (`ThumbnailServices`). A `@ModelActor` built on the main
  actor runs on it, so each card's picture was decrypted, downsampled and PNG-encoded on the main thread; the Time
  Profiler put 30% of card-body time there. The p50 switch time did not move (the cards of that run were mostly text);
  the worst switch fell from 132 to 79 ms and a picture card no longer stalls the frame it appears in.
- **A switch keeps the same row** (offset and opacity ease, `collectionSwitched`) instead of `.id(selectedCollectionID)`
  throwing the scroll view away. Worth about 4 ms and the second live row; the direction cue is kept.
- Tried and dropped: a 150-card page instead of 1,000 changed nothing (p50 67.7 ms) and would have changed End and Select All.

## What a collection switch still costs (68 ms) — the next target
`PROFILE=1 scripts/bench-shelf.sh` records a Time Profiler trace of one drive and `top_frames.py` lists main-thread frames.
Over a switch, 99% of the main thread is SwiftUI's graph update, half of it laying out the row's `ForEach`, and
`ClipboardCard.body` is 31% of it. Inside a card body: SwiftData property getters instantiate key paths on each access
(`_swift_getKeyPath` 13%, `ClipboardItem.metadata` 13%, read 10 to 20 times a body), the context menu is built on every
body (11%), accessibility strings are built on every body (11%), and the footer's `ViewThatFits` lays out three footers
(10%). The smart-collection rule is 2%. These, and the main-context save and `HistoryStore.apply` that a link
preview's first fetch causes while scrolling, are PR 3.

## PR 3: link fetches wait for a still shelf; the thumbnail cache matches its budget
- `ActivityGate` (Core): the shelf reports scrolling (the scroll offset changing) and every arrow press; a link preview's
  fetch, which ends in a re-sealed record, a save and a rebuild of the history index, starts when nothing has moved for
  250 ms. Nothing is cancelled or skipped: the preview arrives a beat after the scroll stops. `ActivityGateTests` cover
  waiting, extension while activity continues, and cancellation.
- **The bench had never fetched a link.** `LinkPreviewPolicy` returns false in UI-test mode whatever the setting, so the
  "Link Previews on" runs above measured a shelf with none. It now follows the setting in a UI-test launch only when a
  benchmark names the local stub (`PESTO_UITEST_LINK_STUB_MS`), which makes no request. With fetches running, arrow
  steps still measure 12.9 ms p50 / 15.2 p95, and a fetch's save costs 1.3 ms and its index update 0.5 ms on this Mac
  (`metadataSave`, `historyApply`), so the gate matters for a Mac that is several times slower, with a history that is.
- `ThumbnailCache` was 24 MB and 40 entries while `budgets-2026-10.md` records 48 MB; it is 48 MB and 100 entries. The
  pictures history still measures 120 MB against the 150 MB budget (`scripts/check-memory-budget.sh 150 pictures`).

## Final (after the review's fixes; same Mac, Profile build, one run each — run twice before trusting a small gap)
| History / drive | Commit time p50 / p95 / max | Baseline (`imported` only, before any fix) |
|---|---|---|
| imported, one arrow press | 15.1 / 26.5 / 32.1 ms (a second run of the same code: 12.9 / 15.2 / 18) | 39.9 / 58.3 / 59.7 |
| imported, held arrow | 12.8 / 15.9 / 68.5 ms | 135 / 485 / 765 |
| imported, ⌘] through the collections | 49.4 / 68.3 / 79.4 ms | 70.7 / 84.3 / 132 |
| mixed, press / held arrow | 24.7 / 27.4 ms, 12.6 / 14.0 ms | not measured before |
| large (5,000 text), press / held arrow | 21.5 / 26.7 ms, 12.7 / 13.8 ms | not measured before |
View bodies per step: ClipboardCard 3 (was 30 per press, 69 per held step), GridView 1, OverlayRootView 0.

The single press on `mixed` and `large` is slower than a repeat because a first press glides (`scrollToFocused(animated:)`)
and the step is timed to its first frame; a held arrow does not animate. Collections on `mixed` and `large` are two
(none): their switch numbers prove nothing.

The review of the whole change found and fixed: two edges the Core directory graph forbids (`Storage->Seeding` through the
stub's picture, `Seeding->Predicate` through the smart collections; `CoreDirectoryCycleTests`), a collection-switch ease
that would not have animated (two writes in one turn), and an ease that bypassed `Motion`. Left as noted: `ThumbnailServices`
keeps one service per container for the life of the process (a restore that replaces the container leaves the old one
alive), and `ClipboardCard ==` assumes the main thread, which is where SwiftUI compares.

## Not measured, and what to do on the slow Mac
Nothing here ran on the work MacBook. Its store is sealed with that Mac's Keychain key, so its clips cannot be opened
elsewhere; `make bench-shelf` on a build with this change, on that Mac, compares like with like (the `imported` seed has
its shape). If a hitch remains, `PROFILE=1 scripts/bench-shelf.sh` on it names the frames.

## Held ⌘] (added after review)
A held ⌘] repeats every ~30 ms and a switch costs ~50 ms, so each repeat queued behind the last (`benchCycleHold`: 40
switches at key-repeat pace; 83 ms p50, 265 p95, 318 max per switch before). `cyclePinboard` now applies the first press
at once and adds up presses that follow within 80 ms (`ShelfMotion.cycleCoalesce`) into one switch.

| ⌘] held (40 presses), imported | Before | After |
|---|---|---|
| Key to commit (`collectionKey`) p50 / p95 / max | 82.6 / 265 / 318 ms | 1.0 / 36.3 / 68.2 ms |
| Switches actually drawn | 40 | 20 |
| Single presses, 600 ms apart (`collectionSwitch`) | 49–55 ms | 55 ms (unchanged, noise 49–70) |

Tradeoff: with the key held the chips and the row move in steps of one or two collections instead of every one (the last
press always lands). Tried in the same pass: building the card's context menu lazily (`DeferredCardContextMenu`, 11% of a
card body in the profile); the single-switch number did not move outside run-to-run noise on this Mac, so treat it as
reasoned, not measured.

## Where a collection switch's 50 ms goes (bisect, `imported`, two runs where noted)
`DRIVES=benchCycleCollections scripts/bench-shelf.sh` with the card body swapped for a smaller view (a temporary
experiment, not committed). Commit time p50 per switch, about 8.5 card bodies realized per switch:

| What a card draws | p50 |
|---|---|
| A flat rectangle (the floor: `LazyHStack`, `ForEach`, tasks, row fade) | 10.5 and 16.8 ms |
| The card's content only (`standardCard`: header, text, footer) | 36.4 ms |
| plus the decorations (`decoratedCard`) | 39.1 ms |
| plus hover and popover layers (`popoverCard`) | 43.8 ms |
| The full card (tasks, gestures, accessibility, context menu, drag) | 49.4 and 50.4 ms |

So the lazy stack is not the cost (about 12 ms of 50): the content of a card is about 20 to 25 ms (about 3 ms a card), the
layers around it 8 ms, and the modifier chain 6 ms. Skipping the header, the content or the footer one at a time moved the
number by less than the run-to-run noise (30 to 37 ms against 36), and skipping all three still read 42 ms, so the cost is
not in one of them: it is in what the card works out for itself before drawing (its treatment, concealment, preview text,
accessibility strings and a dozen SwiftData reads, each instantiating a key path; 10 to 20 `metadata` reads a body).
The next step is to compute all of that once per clip, off the main thread, into one value the body only reads, rather than
shaving single calls: a lazily built context menu changed nothing measurable on its own.

## Correction: card body code is 14% of a switch, so a once-per-clip display model would not fix it
The section above guessed the card's own derived values (treatment, concealment, accessibility, `metadata` reads) were the
cost. `RenderProbe.timed` now adds up how long `ClipboardCard.body` took to build (`CardBodyUs` in `make bench-shelf`),
apart from the layout and drawing SwiftUI does after it:

| `imported` | Body build time per step | Of the step's commit time |
|---|---|---|
| ⌘] switch (8.6 card bodies) | 6.6 ms (0.77 ms a body; max 10.9) | 48 ms |
| One arrow press (3 bodies) | 1.9 ms (0.65 ms a body) | 12.5 ms |

Even a body that cost nothing would save 6.6 ms of 48. The other ~35 ms of a switch is SwiftUI building, sizing and
placing each card's view tree (stacks, text layout, the footer's `ViewThatFits`, a dozen modifiers that each add a node),
which the bisect above also shows (the content-only card at 36 ms had none of the derived values in its modifiers). So the
lever is a simpler tree per card (fewer nested stacks and modifiers, one footer layout, less text laid out than is
shown), judged with `CardBodyUs` and the commit time together. It changes how the card is built, so each step needs the
card snapshot tests to stay identical.

## Simplifying the card's tree: five probes, one lever (interleaved A/B, `imported`, 72 switches per side)
A consultant review of the card's view tree ranked candidates; each was probed in the way most favourable to it: the flag
removes (or caches) the piece entirely, and `benchCycleAB` alternates off and on inside one launch, so launch-to-launch
noise cancels. The null A/B (a flag nothing reads) reads 62.14 against 62.22 ms, so differences of 3 ms or more mean something.

| Probe (B on) | A off p50 / p95 | B on p50 / p95 | Verdict |
|---|---|---|---|
| Cache `ParagraphColumn.arrange` (text measured once per width, not twice) | 59.8 / 72.1 | 62.7 / 72.8 | no gain |
| Footer without `ViewThatFits` (one line, upper bound) | 60.9 / 70.3 | 62.1 / 66.1 | no gain |
| No hover-anchor `NSViewRepresentable` per card (upper bound) | 60.8 / 71.5 | 63.3 / 69.4 | no gain |
| 200 characters of text laid out instead of up to 500 | 62.3 / 71.0 | 64.2 / 70.9 | no gain |
| No collection badge (a glass panel on every card in a collection; upper bound) | 61.2 / 71.1 | 56.9 / 61.1 | about 4 ms p50, 10 ms p95 |

So the card's tree has no single piece worth removing: text, footer and anchor cost nothing measurable, which is why the
bisect found no part. The one visible lever is the glass behind the collection badge (`.glassPanelBackground`, a
`.glassEffect` per card on macOS 26). Replacing it with the material the macOS 15 path already uses would save about 4 ms on
a switch over a collection and change how those cards look on macOS 26 (no snapshot covers a card in a collection), so it is a
design decision, not part of this change. Nothing from the probes was kept.

## The collection badge is a material, not glass (shipped)
A card in a collection drew its badge with `.glassEffect` (macOS 26): one glass layer per card. The real swap to the material the
macOS 15 path already used, in two interleaved A/B runs of 72 switches a side on `imported`: p50 61.4 → 52.2 ms and 59.8 →
53.1 ms, p95 69.0 → 62.6 ms and 68.1 → 62.5 ms (about 8 ms, 12 to 15%; removing the badge entirely had measured 4 ms, so the
glass itself was dearer than its layout). The look: a slightly darker flat capsule without the glass's thin lit rim, same icon,
text and position (checked on the real shelf window; an offscreen render cannot draw Liquid Glass). The shortcut keycap was
never glass (a flat fill and a stroke). `docs/images/` pictures of cards in a collection are retaken with `make pictures`.
