# 0052. The iPhone and iPad widget shows a small sealed snapshot of recent clips, kept only while a widget is installed; a tap copies through the app

Status: Accepted (owner request, 2026-11-15)

Extends ADR 0002 (sealed at rest), ADR 0003 (secrets are masked and shown on request), ADR 0046 (Pesto on iPhone and iPad), ADR 0047 (the share extension's sealed inbox) and ADR 0051 (the AutoFill set, whose sealing this reuses). Nothing they decide is reversed.

## Context
A Home Screen widget is a separate process (`PestoWidget`, `net.copypesto.pesto.widget`) that WidgetKit starts whenever it wants a timeline, with Pesto not running. Giving it the store or the history key would put every clip's key into another process, as ADR 0047 and ADR 0051 refused for the other extensions. A widget also cannot read the app's preferences, so it cannot know the theme.

## Decision
**Recent Clips**, kind `AppIdentity.widgetKind`: `systemSmall` (the latest clip), `systemMedium` (three) and `systemLarge` (six), two and three at an accessibility text size (`WidgetSize`). No Lock Screen families, no Live Activity, no controls, no buttons inside it. Each clip is drawn in the card's language at widget scale: text, a link's host large with its path small, a color as its swatch with its hex, a picture as a thumbnail, code in monospace, a file by name; one quiet foot line with the source (the app, Another device, or how it came in on this device, ADR 0049) and the age as the card writes it (`CardAge.text`, moved by timeline entries at each minute or hour it changes, `WidgetContent.refreshDates`). The ground and accent are the theme's, carried in the snapshot. Clip content is `.privacySensitive()`, so iOS redacts it where the person asked it to (a locked device). No snapshot reads "Open Pesto to show your clips"; an empty one "No clips yet".

**The snapshot** (`WidgetSnapshot`, chosen by `WidgetSnapshotSelection`): the newest eight clips that `ShortcutClipSearch.isOfferedOutsidePesto` allows (never a secret, a clip still being judged, one the content filter flagged, or one that expires), each as its id, kind, the first 200 characters of its preview (never its whole content), a link's host and path (120 characters each, no query or fragment, from `LinkDisplay`), a color's six hex digits, a source label (60 characters), its date and pin flag, and for a picture a JPEG thumbnail at most 240 pixels on its longer side and 24 KB (`ImageDownsampler.thumbnailJPEG`), at most 160 KB of thumbnails in all; plus the theme's light and dark ground and accent. It never holds a clip's full text, a note, tags, a title the person typed, the collection, a file's folder, the source app's bundle id or anything of a covered clip.

**Sealing.** The format and key handling of ADR 0051 are now shared (`SealedFileFormat`, `SealedFileEnvelope`, `SealedGroupFile`, `SharedFileKeyStore`): the file is `widget-snapshot.pestowidget` in the app group, `PESTOWGT`, a version byte, then AES-GCM-256 over the JSON with the header and the purpose `pesto.widget-snapshot.v1` as associated data; written whole, atomically, with complete file protection; read with a 256 KB bound, which the largest snapshot the bounds allow still fits. The key is a random AES-256 key of its own (account `AppIdentity.widgetKeyAccount`) in a Keychain group of its own, `$(AppIdentifierPrefix)net.copypesto.pesto.widget`, this device only, never synchronized, readable after first unlock. The widget's entitlements name that group alone, so it cannot read the quick-insert key and AutoFill cannot read the widget's; the app lists it third, after its own group and the quick-insert group. **This key opens only that file.**

**When it exists.** Only while at least one Pesto widget is on the person's Home Screen (`WidgetCenter.getCurrentConfigurations`, asked when Pesto becomes active and when it leaves the foreground); with none there is no file and no key, and the Keychain is not touched. There is no setting. While a widget is installed the snapshot is rewritten a second after a save changes the history, one write at a time (so an older snapshot never lands after a newer one), and the app then reloads the widget's timelines. Clear History writes an empty snapshot at once. The iOS app has no History Lock and no Hide Clip Contents today (the Mac's cover is a screen-share defence; iOS has no such state), so there is no other state to empty it for; one added later must empty it too. The widget only reads the file, on each timeline request, and keeps nothing decrypted between them; any failure draws the unavailable state.

**A tap.** Each clip is a link `pesto://clip/<UUID>` (`WidgetLink`; in the small family the whole widget is the one link). The app registers the `pesto` scheme, as the Mac does. It acts only on exactly that shape: the scheme, the host `clip`, one path part that is a UUID, and no query, fragment, user or port; anything else is ignored. A link to a clip that is still eligible copies it through the library's one copy path (the "Copied" notice, the clip moved to the front) and shows the library on All with that card flashed; an unknown or no-longer-eligible id only opens the library. A link opened from elsewhere can do no more, since it copies only what the widget may show.

## Consequences
- What sits outside the store while a widget is installed: up to 256 KB of the newest non-secret previews and small thumbnails, sealed, in the app group, and a key in a Keychain group the app and the widget share. Code signed by the same team could read both, as with the inbox and the AutoFill set; nothing else can.
- A clip deleted or made secret leaves the snapshot within about a second of the save while Pesto runs; the widget shows the old one until WidgetKit asks for a new timeline after the reload. If Pesto is killed in that second, the next foreground rewrites it.
- A widget removed while Pesto is away leaves the file and key until Pesto next becomes active or leaves the foreground.
- On a device: an App ID for `net.copypesto.pesto.widget` with the app group and Keychain Sharing, in its provisioning profile, and the main app's profile carrying the new Keychain group.
- A Mac widget is not part of this: it needs the Mac app's own signing decision (a Developer ID profile with an app group the sandboxed widget can share).

## Docs affected
`AGENTS.md` (security invariant 2's exceptions, the Mobile paragraph), `docs/testing.md` ("The iPhone and iPad app"), `docs/design/ios-library.md` (widgets were left out). The README and the guide say nothing about the iPhone app until it is released (ADR 0046); the snapshot joins the privacy page's exceptions in the release that ships the app.
