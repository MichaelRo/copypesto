# Core/Paste — notes

Focus restoration, accessibility direct-write, CGEvent keystroke fallback. The paste flow spans this module, `App/AppDelegate.swift` (orchestration), and `Features/Overlay` (panel/trigger timing — see its `CLAUDE.md`). See ADR 0009 for the three-tier strategy.

## High-Risk Zones

| Path | Blast radius |
|---|---|
| `App/AppDelegate.swift` | Owns `executePasteItem(_:)` and `currentPasteTask`; the wake/lock handler only cancels `currentPasteTask` (invariant below). |
| `FocusRestoration.swift` | Captures/restores the target app; a miss pastes into the wrong window or Pesto itself. |
| `KeystrokeSynthesizer.swift` | Synthesizes ⌘V via CGEvent; timing and tap-type are load-bearing. |
| `AccessibilityWriter.swift` | AX direct-write path (tier 1 of the paste strategy). |

## Key Invariants

- **Snippets and the suggestions are designed in `docs/design/snippets-and-suggestions.md`**: a snippet is a pinned clip whose text holds `{{placeholder}}`, expanded in the paste flow before the write, with no snippet model.
- **A snippet that asks for values shows its prompt inside the paste task** (ADR 0017, `AppDelegate.expandedPayload`, now `async` and nil when cancelled). Capture the target (`focusRestoration.capture()`) *before* it so `{{app}}` and the later focus restoration know the app; the prompt is a non-activating panel that can become key (`FillInPromptWindowController`), so the target stays frontmost. Every caller returns nil on a cancelled prompt, and the prompt closes (answers nil) when the task is cancelled by sleep, lock or a newer paste. A stack asks for all its snippets' fields before the first clip (`AppState.expandedStackItems`), never in the middle of a ⌘V. Not verified on hardware: that the target regains the keyboard as quickly after the prompt closes as after the shelf (`docs/testing.md`, manual checklist); if it does not, pasting drops silently as in the lesson below.
- **A value typed into a fill-in is inserted literally.** `TemplateExpander` expands in one pass over the template, so `{{clipboard}}` typed into a field pastes as those characters. An optional section is resolved on the template before the pass.
- **Restoring focus from a `.accessory` app requires `AXUIElementSetAttributeValue(kAXFrontmostAttribute)`, not `NSRunningApplication.activate()`.** On macOS 14+, `activate(options:)` is deprecated and `activateIgnoringOtherApps` is silently ignored; `activate(from:)` requires the sender to be frontmost — which `.accessory` apps never are. Fix: `AXUIElementSetAttributeValue(AXUIElementCreateApplication(pid), kAXFrontmostAttribute, true)` (requires AX permission) + `target.activate(options: .activateIgnoringOtherApps)` as backup. **Then wait for the keyboard, not for a time** (ADR 0009): the target is already frontmost, but its window is not key until the window server has handed the keyboard back after the shelf's `orderOut`, and a ⌘V posted earlier is silently dropped. `FocusRestoration.waitForKeyboardFocus` polls `KeyboardFocusProbing` (the system-wide focused application) every 5 ms and returns when it is the target; 500 ms (200 ms after an activation notification) are only the ceilings, and what is waited out without Accessibility. Do not put a fixed sleep back: it was 530 ms of every paste. `make bench-latency paste` is the guard (a dropped paste is a row with no arrival).
- **Text over 200 KB is pasted with ⌘V, not written into the field** (`PasteCoordinator.usesDirectWrite`): the target inserts a directly written string on its own main thread (970 ms for 5.4 MB).
- **`CGEvent.post(tap: .cghidEventTap)` DOES need Accessibility permission to be delivered.** Without it macOS silently drops the synthetic ⌘V and `post` returns no error, so the coordinator checks `CGPreflightPostEventAccess() || AccessibilityAccess.isTrusted` first and falls back to the manual-paste toast (`PasteCoordinator.keystrokeTier`). (This note used to say the opposite; that was the cause of "auto-paste doesn't fire".)
- **Every paste must be started through `AppDelegate.runPasteTask` (which uses `PasteTaskTracker`).** The tracker cancels the paste already in flight, only lets a task clear its own entry, and is interrupted by sleep, wake and screen lock; a paste requested under an older interruption epoch is refused. Any unstructured `Task { await executePaste(...) }` bypasses all of that and can fire a phantom paste into whatever app is focused on return. Also: `group.cancelAll()` does NOT cancel underlying Task objects referenced inside `group.addTask { await someTask.value }` — cancel the underlying tasks explicitly after `group.next()`.
- **Every pasteboard write Pesto makes for a paste goes through `OwnWriteGate.write(to:_:)` (`AppState.writeToPasteboard`).** The gate marks the write in flight (the watcher defers its tick) and records the pasteboard's change count afterwards; the watcher ignores every change count up to that mark. This replaced `skipNextCapture()`, a counter that assumed one write bumps the change count exactly once — a mismatch swallowed the user's next real copy. Writes that *should* be captured (`CopyItemCommand`, `CopyToPestoIntent`, the AI-result Copy button) stay off the gate. AppleScript and URL-scheme paste paths must call `executePasteItem(_:)` (which captures focus synchronously then runs the write/execute in a stored paste task) — never set `isOverlayVisible = false` to trigger paste on an already-hidden overlay.
- **Every item write goes through `AppState.writeItem`, and every stored type that a plain-text field cannot read gets a `.string` flavour (`PasteFlavors`).** Web and Electron fields ignore `public.url` and `public.rtf`. ⌘V uses the key code `KeyboardLayoutKeyCode` finds for `v` (Dvorak, AZERTY), falling back to 0x09.
- **The 15-second capture deadline counts from when the shelf was hidden, not from when it opened** (`FocusRestoration.markHidden()`, called by `handleOverlayHidden`): a person who searches for 20 seconds still gets the paste. `capture()` refuses Pesto itself as a target. The activation wait observes `NSWorkspace.shared.notificationCenter` (not `NotificationCenter.default`) and re-reads the frontmost app when it times out; ⌘V is posted only while the target is still frontmost (`keystrokeTier(canPost:targetIsFrontmost:)`). Accessibility calls run off the main actor with a 0.5 s messaging timeout (`AccessibilityTimeout`).
- **`AppState.writeItem` returns nil, and writes nothing, when the history is locked or a clip's blob exists but will not open** (the person is told). A nil must stop the paste: never fall back to the preview, which is 500 characters of the text or a secret's mask text. Callers `guard let`.
- **A pasted secret leaves the pasteboard after `AppState.secretClearDelay` (30 s)** unless the change count moved (`scheduleSecretClear`, through the own-write gate so the watcher ignores the clear). `writeItem`, `writeText(_:protected:)` and `writeStackItem` schedule it, so a stack restarts the timer with every secret it readies and the last one is cleared too; a stack that waits more than 30 s for ⌘V finds the board empty.
- **Global hotkeys must not shadow system shortcuts.** ⌘⇧⌥V is Paste and Match Style; plain-text paste defaults to ⌃⌥⌘V and is user-configurable. ⇧⌘V (the shelf) is a deliberate exception, kept for parity with the apps people switch from, and paste-previous has no default (ADR 0012).
- **The manual-paste toast says why only when it can say something true** (`ManualPasteToast.choose`): without Accessibility, once per launch, never to a person who declined auto-paste (`Setting.declinedAutoPaste`). A keystroke that failed with Accessibility on is the bare line.
- **A drag to the Finder needs a file** (`DragFile`): the data representations work for fields and editors, and the Desktop takes files. The files are owner-only under `pesto-drag-*` in the temp folder and are swept with the Quick Look folders at launch and at the lock.
- **A shelf paste records its use on the storage actor** (`AppState.notePastedInBackground`), not with a main-context save between the key press and the paste. Hypothesis behind it, not yet measured on hardware: the second paste of a clip felt faster because the clip was already first and the history had nothing to reorder; check with `make bench-latency paste` after touching this.
## Lessons

- **Every pasteboard writer for a secret needs its own 30-second clear and its own test.** The stack once wrote its clips beside the four writers that schedule the clear, so nothing failed; `PasteboardWriteSourcesTests` checks only the concealed marker. A stack readies each clip before ⌘V, so a secret waiting longer than 30 s is cleared and the keystroke pastes nothing.
- **`NSPasteboard.setData` does not bump the change count; only `clearContents` does.** A writer that clears the board and then takes time before `setData` hides its clip from a poll in between.
- **Wait for the keyboard, not for a fixed time.** A paste into an already-frontmost app once waited 500 ms for the window server; the system-wide focused application says when the keyboard is back (`KeyboardFocusProbing`).
