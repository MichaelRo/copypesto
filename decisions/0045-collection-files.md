# 0045. A collection is shared as a `.pesto` file that carries its pictures and whole texts

Status: Accepted (owner request, 2026-11-13)

Extends ADR 0002 (what is sealed at rest), ADR 0003 (secrets), ADR 0008 (Undo) and ADR 0011 (importers go through `ingest`). Nothing they decide is reversed. The text-only collection file of earlier versions (version 1, `.json`) is replaced as the thing Pesto writes and stays readable.

## Context
Export Collection wrote a JSON file of text clips, each cut to its 500-character preview. A collection of screenshots, files or long snippets arrived as nothing, or as a stub. Import was reachable only from Settings, and a file the person received had no type, so double-clicking it did nothing. The owner asked for "a way to import a collection" from the shelf too, a file that carries pictures and files within size limits, and the backlog item "Shareable Collection Packs".

Checked while deciding:
- A version 1 export of a hidden or secret clip wrote its **masked preview** (`Hidden by 1Password`, `•••• 1234`) as an ordinary text clip, and an import turned that mask into a real clip. No real secret text was written, but the file was wrong and a hidden clip's title and note were exported with it.
- `StorageService` keeps one sealed blob per clip (`ClipboardBlob`) holding the bytes the clip was captured with, and its `mimeType` is the pasteboard type they came from. A **file clip is a file URL, not the file's contents**: Pesto never reads the file.

## Decision
**Format.** Version 2 is the same JSON (`version`, `collection`, `items`). Per item it adds two optional fields: `payloadType` (the type identifier the data was stored under) and `payload` (the data, base64). `previewText`, title, note, tags, pin, time and source app stay, so a version 1 reader still imports the text items. Unknown fields are ignored. A file from a version above 2 is refused. It is still **one JSON file**: a package folder is zipped badly by mail and AirDrop.

**What round-trips.** Text, code, links and colors (the whole text, not the preview); pictures in the formats Pesto captures (PNG, TIFF, JPEG, HEIC, GIF, WebP, PDF) with their bytes, except SVG (below); **file clips are left out and counted** (owner decision, 2026-11-13). A file clip is only a path: it names the person's folders, points at nothing on another Mac, and carrying contents would mean reading arbitrary files at export and writing files at import. An import also skips and counts any `public.file-url` payload in a received file (hand-made or from an earlier build of this branch); it never creates a file clip from a file. Formatting of a rich-text copy (RTF, HTML flavors) and a link's preview image do not travel; a picture's text is read again on the new Mac.

**This is a plain file the person chose to write**, as version 1 was: it is not sealed, and anyone who gets it can read it. The save panel is the consent, and the privacy guide says so.

**What is never written.** A file clip is counted as a file. A clip with a sensitivity category (secret, credit card, hidden/credential copy from an allowed password manager), a clip not yet judged (`analysisPending`), and a text in which the detector finds a secret now. They are left out and counted, never masked into the file. A clip over the caps is left out and counted. A text clip whose data cannot be opened is exported as its preview, as before; any other kind is counted as unreadable.

**Caps.** One file holds at most 1,000 clips (`CollectionFilePolicy.maxClips`): an export keeps the newest and counts the rest, an import refuses a larger file before it adds anything. One clip's data is at most `UndoPolicy.maxClipBytes` (4 MB; the same "a clip this size is not held" line), the whole file at most `HistoryExporter.maxImportBytes` (64 MB, the existing import bound). A file is checked by size before it is read, a base64 string by length before it is decoded, a picture by its header (at most 50 megapixels, since a byte limit does not bound a decode).

**Retention.** An imported clip enters the history now (`timestamp` is the time of the import), and the file's date is kept only as when it was first copied (`adoptFirstCopy`, ADR 0021). A file's own dates would be older than the retention age and the next sweep would delete the clips; 1,000 clips at once could also push the person's oldest clips out of the item limit. So the question before an import (always for a file from Finder, and for a panel import whenever it applies) says "Up to N of your oldest clips will be removed to fit your limit" and keeps Import and Cancel. N is an upper bound (it counts every unpinned clip as new).

**Import** goes through `StorageService.ingest` (ADR 0011: the only path that seals under the history key, masks, classifies and dedupes; the importer needs a `StorageService`, so the app passes its own). New ids are made for the clips and the collection: nothing of the file's ids is kept (a received id could collide with, or be made to stand for, something the person has), and a clip the history already holds is found by its content. A clip already in the history that belongs to no collection is put into the imported one and counted; one in another collection stays there. (Undo takes back the new clips and the new collection; it does not take back that move, because an Undo entry removes what it added and cannot hold a change to an existing clip.) The collection is matched to an existing one by name only. Its name loses control and format (bidi) characters and is cut to 100 characters; its icon must be one Pesto offers or a single emoji, its color six hex digits, otherwise the default; a smart collection arrives as a plain collection, because a rule from a file is not validated. Per item, in order: a file reference is skipped and counted; already here (id, tombstone, or the same content hash) is counted and skipped; a source app on the exclusion list is skipped and counted with the secrets (ADR 0004); a payload is checked (type on a list of capture types, valid base64, size, text is UTF-8, a file clip is a `file:` URL, a picture opens); then `ingest` with the file's id and its time (a date after now is brought back to now, or a clip would stay at the front of All for good), no text rewriting and no look-alike dedupe. The kind comes from the data and its type, never from the file's `type`. The result is a value: imported, already here, too large, left out as sensitive, left out as a file, unreadable. The history key is read with `try`: a key that cannot be had fails the import instead of storing clips under a plain hash. An item without a payload (a version 1 file) takes the earlier text path, which now also counts what it skips. An item that fails to store is counted as unreadable and the import goes on. The clips are filed and annotated in batches of 25 after the background analysis, from a fresh context, and the ids are kept as they are added, so the Undo entry covers what came in even when an error ends the import. Undo is as before: one action for up to 200 clips, plus the collection if the import created it.

**The `.pesto` type.** Extension `pesto`, identifier `AppIdentity.bundleID + ".collection"` (`net.copypesto.pesto.collection`), exported in `Info.plist` conforming to `public.json` and `public.data`, with a Viewer document type and `LSHandlerRank` Owner. Export writes `<name>.pesto`; the import panels accept `.pesto` and `.json`.

**Opening from Finder, AirDrop or a double click.** `application(_:open:)` hands a file URL to the import flow. The file is judged by name, kind and size alone (`CollectionFileType.openVerdict`). Several files opened together are imported one after another, never with two questions on screen. Opening is refused with a message before onboarding, while the history key is unresolved, or before the store is ready (a double click never creates the key). The file is read as a regular file only (a pipe or a folder is refused, a link is followed and checked on the open descriptor, at most 64 MB are read), off the main thread, to a preview (name, clips that can come in, how many of the oldest clips the limit would remove). An alert asks "Import “name”?" with Import and Cancel, and only then the History Lock is honored through `ProtectedAction` (Touch ID or the password; refused with a message otherwise). Nothing is imported silently. A file chosen in an open panel skips the question unless the retention warning applies (choosing it is the consent). Every path ends with a message saying what came in and what was left out.

**Where.** The shelf: *Import Collection…* is in every collection chip's context menu beside *Export Collection…* (and an Import accessibility action), and in the right-click menu of the + (New Collection) button; one click on + still makes a new collection. Settings → Collections keeps its Import… button; both call `AppState.importCollection`, which closes the shelf before the panel as Export does.

**SVG is not importable.** Its picture is drawn by the system's SVG renderer, and whether that renderer ever fetches a linked address could not be established, so Pesto does not take SVG in a collection file (an SVG source that Pesto keeps as a text clip is text and does travel). A PDF must open with `CGPDFDocument` and have a page.

**Memory.** Reasoned, not measured. An import reads at most 64 MB, decodes it to records (Foundation's decoder holds a tree of the whole file while it works, a small multiple of the file), and drops the file's bytes before any clip is added. Each record's base64 text is released as its clip is stored, so after the decode the live data is the records without their payloads plus one clip (4 MB, its decoded copy and the ingest's work). The question before an import decodes the file once more, off the main thread, without keeping it. An export holds the clips' base64 (at most 64 MB, estimated with the titles, notes and tags counted) and the encoded file; it is written without pretty printing and without escaped slashes, which would add a byte to every `/` of the base64 text.

**Source apps and dates.** A file carries each clip's source app (name and bundle identifier) and the time it was copied, as version 1 did; the privacy guide says so. The bundle identifier is what lets an import skip a clip from a private app.

## Consequences
- A shared collection now holds what the person sees, within 4 MB a clip. A collection of large screenshots will skip some, and says how many.
- A secret never reaches a shared file, even masked; a collection with some secrets exports fewer clips than it shows, and the message says so.
- File clips never travel, so a collection of files exports fewer clips than it shows, and the message says how many were files.
- Importing 1,000 pictures runs OCR and the other background analysis for each picture, one batch of 25 at a time, so a big pack takes as long as copying that many pictures.
- Import is in each chip's menu, the + button's right-click, Settings and by opening a file. No new visible control crowds the chip bar.
- Pesto registers as the owner of `.pesto`, so a double click opens it in the menu-bar app. The document has no icon of its own yet.
