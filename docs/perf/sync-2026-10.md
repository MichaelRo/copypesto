# What sync costs (2026-10-30)

Measured with `SyncPerformanceTests` (`make bench-sync`, which sets `PESTO_SYNC_PERF_CLIPS=5000`; the full log is `.build/xcode/bench-sync.log`, Debug build, in-memory stores,
a temp folder) on a developer Mac (M-series MacBook Pro, macOS 27). Two simulated Macs in one process, so each figure includes both sides.
Real iCloud latency is not measured here; it waits for the two-Mac check (`docs/testing.md`).

| What | Result | Budget |
|---|---|---|
| A copy with sync off, this branch | 2.55 ms per clip over 5,000 | 50 ms (`CopyLatencyPerformanceTests`: 2 to 3 ms) |
| The same loop on `main` before sync | 2.63 ms per clip | the baseline above |
| A copy with sync on (journal stamps each save) | 3.5 ms per clip | 50 ms |
| First send of 5,000 clips | 2.3 s, 2.3 s CPU, +5.5 MB | one time, in the background |
| First receive of 5,000 clips | 17 s, 13 s CPU, +16 MB | one time, on the storage actor, not the main thread |
| An idle pass (nothing changed) over 5,000 clips | 1.1 to 1.5 ms | every 30 s that is under 0.005% of one core (budget 0.5%) |

Sync off adds nothing measurable: the new columns are optional strings and the save hook returns at once when the journal is off.
What it found: one pass sent at most 4,000 clips (20 batches of 200) and left the rest for the next poll, so a first send of a large history
now continues at once (`Timing.batchesPerPass`).

Receive, after skipping the lookups for deletions when there are none (the common first join): 2,000 clips took 6.3 s instead of 7.9 s
(about 20% less). The rest is the shared copy pipeline (2.5 ms a clip) and one more save per clip; a path that bypasses them would touch
sealing and masking, so it is not done. Measured with a lookup-only second pass: the four fetches per record cost about 1.3 ms of the 3.1.

Tried and dropped (2026-10-30): asking the store once per 300 records which clips and texts are already here, instead of once per
record. With the lookups cached the receive of 2,000 clips took 6.2 s against 6.3 s, within noise: a lookup that finds nothing is
cheap, and the cost is the shared copy pipeline and one more save a clip. A first version looked 15% faster only because a bug skipped
the work after the insert; the convergence tests caught it. Memory after a receive grows about 4 KB a clip (+8.8 MB for 2,000), the same
as the backup writer's SQLite page cache, so smaller batches do not change it. The compaction threshold (100 segments) waits for the
latency numbers (`scripts/sync-latency`).
