# Core/Backup — notes

Backup file format, key store, automatic-backup policy. Restore runs in `Core/Storage/Models/StorageService+Backup.swift`. See `AGENTS.md`, `decisions/0010-backup.md` and `decisions/0010-backup.md`.

## Key Invariants

- **Hashes and ids do not travel between Macs unless made to.** A Mac's stored content hash is keyed from its own blob key, so a backup carries a plain SHA-256 (`plainHash`) and the receiving Mac derives its own. Restore checks "already have it" (`alreadyHas`, by id or content) before `ingest(_:preferredItemID:)`, because `ingest` pops a duplicate to the top and would reorder the history. Dates in backup metadata are exact numbers, not ISO-8601 seconds (clips copied within one second would collapse).
- **Tombstones are by id**, so they remove a clip only on a Mac that got it from a backup with the same id; two Macs that copied the same text merge by content.
- **A later automatic backup reuses the file's header** (the key wrapped by the passphrase), so the passphrase is never kept; `BackupFile.write(records:origin:key:header:)` checks the header against the key first. Automatic backup is off by default and per Mac (`AutoBackupSettings.enabledKey`, not in the settings export); a UI test must never turn it on, because the suggested folder is the real iCloud Drive.
- **The recovery key must never become a clip.** Its Copy button writes through `AppPasteboard.general` with `org.nspasteboard.ConcealedType` (`BackupSheets.swift`), which the watcher drops.
- **A backup is written record by record** (`BackupFile.StreamingWriter`, fed by `StorageService.streamBackupRecords`, which pages through the history and yields between batches) to `<file>.partial` next to the target, and replaces the target only after the manifest is written and `AutoBackupGuard` has passed; a refused or failed run deletes the partial file. `BackupFile.write(records:…)` and `backupRecords` still exist for tests and small histories.
- **Restore reads the file twice, never whole** (`decisions/0010-backup.md`). `BackupFile.verify(url:credential:)` authenticates every chunk and the manifest and keeps only collections and tombstones; `StorageService.restore(_: VerifiedBackup)` then applies those first and streams each clip through `ingest`, re-authenticating it. Read with `pread`, not `FileHandle`: `FileHandle.read` keeps the returned pages resident (an 80 MB file grew memory by 80 MB; `BackupVerifyMemoryTests` guards it). `VerifiedBackup` keeps the descriptor open, so a replaced or deleted file changes nothing. `BackupFile.read(Data)` still exists for tests.
- **A backup never replaces a better one with a worse one** (`AutoBackupGuard`, `AutoBackupService.backUpNow`): refused when storage fell back to memory (`AppState.storeIsOnDisk`), when a clip's blob exists but will not decrypt (`skippedUnreadable`; a clip with no blob at all, such as an old snippet, is `skippedNoPayload` and does not refuse), or when the clip count is under half the baseline (`lastClipCount`, which only rises: `AutoBackupGuard.nextBaseline`, ADR 0010, and falls only by clips removed on purpose: a retention sweep or a confirmed Clear History range, `AutoBackupSettings.lowerBaseline`, ADR 0010) unless the person confirms; Clear Everything resets it. The unreadable clips are listed (`BackupExportSummary.unreadableIDs`) and Settings can delete them (`DeletionReason.unreadable`, no tombstone). The file it replaces is copied to `<name>.previous.pestobackup` first. The file name carries the first 8 characters of the device id; a file under the old name is adopted only when its header equals this Mac's. Set Up refuses (`AutoBackupError.backupAlreadyInFolder`) when the folder holds a backup and this Mac has no backup key, because minting a new key would overwrite the only copy that the old key opens.
- **Every backup carries a file id** (`PSTOFILE` + 16 random bytes after the header, ADR 0010) and its chunks are bound to `SHA256(header | file id)`, because a later backup reuses the header and two backups of one Mac would otherwise share their associated data. Read the first chunk's offset with `BackupFile.chunkBinding`/`firstChunkOffset`, never `headerLength`: a file from before file ids has no block and must still open.
- **A backup carries the settings as record kind 4** (`BackupRecord.settings`, ADR 0010): the file version stays 1 because the stored header is reused for every automatic backup. Core never parses the JSON; `SettingsBackupManager` writes and restores it, and a restore holds back what would delete history. A change to a setting the backup carries notes a backup (`SettingsBackupManager.fingerprint`); the backup's own bookkeeping keys are not carried, so they cannot start a loop.
## Lessons

- **Restore must not replay live-capture policy.** `ingest(_:preferredItemID:rewritesText:)` takes `rewritesText: false` from restore, and `BackupItemMetadata.sensitivityRaw` carries the credential flag; otherwise a credential came back as an ordinary clip and this Mac's paste rules rewrote text whose stored hash was of the original. A test secret must be something the detector does not recognize (a long token is classified as an API key, not a credential).
- **`FileHandle.read(upToCount:)` keeps its pages**: reading an 80 MB backup chunk by chunk still grew resident memory by 80 MB, while `pread` into a buffer stayed at 2 to 6 MB. Measure a streaming claim from a second thread that samples resident size, with the whole-file path as a control (`BackupVerifyMemoryTests`).
- **`NSApp.runModal` (and an `NSAlert` inside launch) does not run main-queue work, so a window with async tasks must not be modal.** The lost-key restore window was first run with `runModal` and hung after its first button (nothing in the sheet's `Task`s ran); `KeyLossRecoveryUITests` found it. The recovery is event-driven now: the alert, then a normal window, then `finishLaunch` from a completion. A hand check could not have told a hang from a slow Keychain.
